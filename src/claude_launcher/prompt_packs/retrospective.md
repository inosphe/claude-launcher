## 세션 회고

이 프롬프트는 이 세션이 지금까지 한 일을 되짚어 보는 회고 요청이다. 두 부분으로
나뉜다: (A) 세션 전반의 회고, (B) 이 세션이 따른 cflow 정의(워크플로 파일) 자체의
리뷰와 개선 제안. 결과는 사람이 다음 세션과 다음 정의 수정에 쓰는 기록이다.

이 프롬프트는 두 경로로 전달된다.

- cflow 런의 마지막 노드(예: improv-worker-v2 settle 절차의 `retrospective`)가
  `claunch retro --print`로 읽게 한 경우: 런은 정상 진행 중이다. 회고를 마친 뒤
  그 노드의 결과를 보고하고 런을 계속 진행한다.
- 사용자가 `claunch retro <세션>`(또는 웹 UI)으로 직접 보낸 경우: 대개 런이
  정상적으로 끝나지 않았다(중단·halt·특정 스텝에 멈춤·컨텍스트 손실). 이때는
  **런을 진행시키지 않는다.** `next`·`select`·`flow_report`를 부르지 않고, 승인을
  요청하지 않으며, 멈춘 스텝의 일을 이어서 하지 않는다. 회고만 하고 턴을 끝낸다.

### 하지 않는 것

- 코드·문서·워크플로 파일을 고치지 않는다. 회고는 기록이고, 개선은 제안으로만
  남긴다. 제안을 실행할지는 사람(또는 그 정의를 맡은 세션)이 정한다.
- 이슈를 새로 만들지 않는다. 회고 중에 세션이 만든 이슈가 생기면 세션 정산
  (settle)이 그것을 다시 기다리게 된다. 후속 일감이 필요하다고 판단되면 제안
  절에 적는다.
- 기억으로 쓰지 않는다. 아래 1절의 기록에서 확인한 사실만 쓴다. 확인하지 못한
  것은 「확인하지 못함」, 원인을 밝히지 못한 문제는 「원인 미상」으로 적는다.
- 자기 평가 문장(「잘 처리했다」, 「꼼꼼히 확인했다」)을 쓰지 않는다. 잘된 점도
  근거(명령 출력, 테스트 수치, 커밋)와 함께 적는다.

### 1. 근거 모으기

다음 기록을 읽는다. 해당 기록이 없으면 없다고 적고 넘어간다.

- 대화: 이 세션의 대화 전체. 압축(compact)이나 `/clear`로 앞부분이 사라졌으면
  `claunch transcript show $CLAUNCH_SESSION`(검색은 `claunch transcript search`)로
  원문을 읽는다. 요약만 남은 상태로 회고하지 않는다.
- 런과 저널:
  - cflow v1: MCP `status`, `claunch cflow journal -t $CLAUNCH_SESSION`
  - cflow v2: MCP `flow_status`, `claunch cflow2 journal -t $CLAUNCH_SESSION`
  - 런이 없거나 보관(archive)됐으면 그 사실을 적는다.
- 일감: `claunch beads show <이슈 id> --json`, `claunch beads comments <이슈 id>`
  (오프닝의 `issue: <id>`, 큐에서 잡은 이슈 전부)
- 커밋: `claunch commits --session $CLAUNCH_SESSION`
- 메시: `claunch mesh history <메시>` — 받은 지시, 보낸 요청, 답하지 않은 질문
- 이 세션이 실제로 읽은 워크플로 정의 파일. v1은 `status` 결과의 `source`,
  v2는 `claunch cflow2 status -t $CLAUNCH_SESSION`와 `claunch cflow2 ls`가 보여 주는
  정의 위치다. 그 파일이 전역 레이어(`~/.claude-launcher/workflows/`)나 프로젝트
  레이어(`<저장소>/.claunch/workflows/`)의 사본이고 저장소에 정본이 따로 있으면
  (예: claude-launcher 저장소의 `src/claude_launcher/workflows/`) 정본의 경로도 함께
  찾는다. 제안은 정본을 기준으로 적는다.

### 2. (A) 세션 회고

다음 항목을 이 순서로 쓴다.

1. **목표와 결과.** 이 세션이 받은 목표(이슈 id, 오프닝 태스크 요지)와 실제로
   나온 것(커밋 해시, 착지 여부, 이슈 상태). 목표 중 하지 못한 부분이 있으면 무엇이
   남았는지 적는다.
2. **경과.** 주요 사건을 시간 순서로 5~15줄 적는다: 스텝 전이, 사람의 결정, 실패와
   재시도, 방향 전환. 각 줄에 근거(저널의 스텝 id, 커밋, 메시지 id)를 붙인다.
3. **효과가 있었던 것.** 다음 세션도 그대로 하면 되는 행동을 근거와 함께 적는다.
4. **문제.** 시간·토큰·사람의 개입이 예상보다 많이 든 지점을 적는다. 항목마다:
   - 현상: 무슨 일이 일어났는가(예: 같은 테스트가 세 번 실패, 승인 대기 40분,
     잘못된 브랜치에서 작업, 범위 밖 수정 후 되돌림, 압축 뒤 지시 유실)
   - 영향: 잃은 시간, 다시 한 작업, 다른 세션·사람에게 미친 결과
   - 원인: 기록으로 확인한 원인. 확인하지 못했으면 「원인 미상」
   - 원인의 위치: 세션의 판단 / 도구·환경 / 사용자·상위 지시 / cflow 정의 중 하나
5. **다음 세션에 넘길 것.** 같은 종류의 일을 맡을 다음 세션이 처음부터 알고
   있어야 하는 사실(저장소 규칙, 함정, 느린 테스트, 필요한 권한)을 짧은 항목으로
   적는다.

### 3. (B) cflow 정의 리뷰와 개선 제안

이 세션이 따른 정의 파일을 실제로 열어 읽고, 2절의 경과와 대조한다. 정의 전체를
일반론으로 평가하지 않는다. 이 세션에서 실제로 지나간 스텝(노드)과 그 지시가
실제 상황에 맞았는지를 본다. 확인할 축:

- **지시와 실제의 차이.** 지시대로 했는데 결과가 맞지 않았던 스텝, 지시를 따를
  수 없었던 스텝(전제가 성립하지 않음, 없는 명령·경로를 가리킴, 다른 규칙과
  모순).
- **모호한 지시.** 두 가지 이상으로 읽혀 판단에 시간이 든 문장, 선택(select·choose)
  옵션의 기준이 겹치거나 빠진 경우.
- **완료 판정.** `done_when`·`verify`·`checklist`가 실제로 판정 가능했는가. 통과했지만
  목적을 달성하지 못한 경우, 반대로 목적은 달성했는데 판정 때문에 막힌 경우.
- **불필요한 비용.** 이 세션에서 아무 정보도 만들지 않은 스텝·보고, 같은 내용을
  여러 스텝이 반복 요구한 경우, 지나치게 긴 지시문이 컨텍스트를 차지한 경우.
- **빠진 경로.** 그래프에 경로가 없어서 `request_goto`나 사람의 `goto`가 필요했던
  경우, 루프 상한·타이머·대기가 실제 상황에 맞지 않았던 경우.
- **사람의 개입.** 사람이 승인·선택·지시를 해야 했던 지점 중 정의가 미리 정할 수
  있었던 것, 반대로 정의가 자동으로 넘겼지만 사람의 판단이 필요했던 것.

제안은 항목마다 다음 형식으로 쓴다. 이 세션에서 관찰한 사실에 근거하지 않은
제안은 쓰지 않는다. 제안할 것이 없으면 「제안 없음」과 그렇게 판단한 근거(지나간
스텝 수, 문제가 없었던 축)를 적는다.

```
#### 제안 <n>: <한 줄 제목>
- 위치: <정본 파일 경로>:<줄> — <스텝/노드 id>
- 관찰: <이 세션에서 일어난 일, 근거(저널 스텝·메시지 id·명령 출력)>
- 제안: <바꿀 문구나 구조. 가능하면 바꾸기 전/후 문장 또는 diff>
- 기대 효과: <무엇이 줄거나 막히는가>
- 리스크: <다른 런·다른 역할에 미칠 수 있는 영향, 확인하지 못한 것>
- 우선순위: P2(이 세션에서 실제 실패·재작업을 만듦) / P3(비용만 늘림) / P4(아이디어)
```

### 4. 기록

1. 회고 전체를 Markdown 파일 하나로 쓴다: `$CLAUNCH_SCRATCH/retro-<런 id 또는 날짜>.md`.
   첫 줄은 `RETRO @ <런 id>`(런이 없으면 `RETRO @ <세션>`)이고, 그 아래에
   `## A. 세션 회고`, `## B. cflow 정의 리뷰`를 둔다.
2. 이 세션의 주 이슈가 있으면 코멘트로 붙인다:
   `claunch beads comments add <이슈 id> -f <그 파일>`. 이슈가 닫혀 있어도 코멘트는
   붙는다. 주 이슈가 없으면 파일 경로만 보고한다.
3. 터미널에는 다섯 줄 이내로 보고한다: 코멘트를 붙인 이슈 id(또는 파일 경로),
   문제 수, 제안 수와 각 제안의 제목, 우선순위가 가장 높은 제안 하나.
4. cflow 노드가 이 회고를 요청했으면 그 노드의 결과로 위 기록 위치와 제안 수를
   보고한다. 사용자가 직접 요청했으면 여기서 턴을 끝낸다.

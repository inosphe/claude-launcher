# 세션 모델 선택의 지속성: 재기동 후 원복 현상과 개선안

상태: 설계 (구현 미착수). 이슈 `claunch-w638`.

세션을 fable로 생성한 뒤 Claude Code 안에서 `/model`로 opus로 바꾸면 웹 UI의
세션 레일은 opus로 표시된다. 그러나 데몬을 재기동하면 그 세션은 다시 fable로
올라오고, Fable 사용 한도에 걸린 세션에서는 다음 형태의 출력이 나온다.

```
You've reached your Fable limit. Run /usage-credits to continue or switch
models with /model.
```

이 문서는 그 원인을 코드 경로로 규명하고 개선안을 비교한 뒤 하나를 권고한다.

## 1. 현상과 원인

### 1.1 세션 정의의 모델 값에는 생성 이후 쓰기 경로가 없다

`SessionDef.model`은 세션 생성 시점에 정해지는 필드다
(`src/claude_launcher/daemon/harness.py:89`). 이 값은 `to_dict`/`from_dict`를
통해 `sessions.json`에 직렬화되고 역직렬화된다(같은 파일 `:190`, `:226`).

`sdef.model`을 참조하는 코드는 세 곳이며 전부 읽기다.

| 위치 | 용도 |
| --- | --- |
| `harness.py:421-435` | 생성 시점 검증 (하네스가 선언한 모델 목록과 대조) |
| `harness.py:844-845` | claude 하네스의 명령줄에 `--model=<alias>` 부착 |
| `harness.py:872-881` | 그 밖의 하네스에서 `model_aliases`를 거쳐 실행 인자 조립 |

생성 이후에 이 필드를 갱신하는 코드는 저장소에 존재하지 않는다. 따라서
Claude Code 안에서 `/model`로 무엇을 고르든 세션 정의는 생성 시점의 값을
그대로 유지한다.

### 1.2 명령줄의 `--model` 플래그는 복원 경로에서도 붙는다

`harness.py:844`의 구문은 복원 분기(`:801-823`의 `if restoring:` 블록, 대화 재개
인자만을 다룬다) 바깥에 있다. 즉 최초 실행과 재기동 복원이 같은
경로를 지나며, 두 경우 모두 `--model=fable`이 명령줄에 실린다.

`SessionManager.restore_all`(`manager.py:1561`)은 `sessions.json`에 남은
정의를 읽어 `restoring=True`로 다시 실행한다(`manager.py:1624`). 재기동이
복원하는 것은 세션 정의이고, 그 정의의 모델 값은 1.1에 따라 fable이다.

### 1.3 Claude Code 자신의 선택은 보존되지만 플래그가 덮는다

프로파일 `nc`의 설정 파일에는 다음 값이 기록되어 있다.

```
~/.claude-launcher/profiles/nc/settings.json
  "model": "opus"
```

같은 프로파일의 트랜스크립트에는 `"model":"claude-opus-5"`가 남아 있다. 즉
Claude Code는 `/model`의 선택을 프로파일 단위 설정 파일에 보존한다. 재기동
시 명령줄에 실리는 `--model=fable`이 이 설정보다 우선하므로, 보존된 선택은
읽히더라도 사용되지 않는다.

같은 프로파일의 `.claude.json`에는 프로젝트별 `lastModelUsage` 키가 있으나
조사 시점의 값은 `null`이었고, 대화별로 모델을 기록하는 필드는 확인되지
않았다. 따라서 Claude Code 쪽의 모델 보존 단위는 프로파일 하나다.

### 1.4 UI가 보여 주는 모델 값은 세션 정의와 출처가 다르다

세션 레일의 모델 표시(`web/static/app.js:3178`의 `rail-model`)는 컨텍스트
판독에서 온다. 그 판독은 트랜스크립트의 assistant 턴에 실린 `message.model`을
그대로 읽은 값이다(`daemon/ctxsize.py:130`). 이 경로는 `sdef.model`을 전혀
참조하지 않는다.

그래서 `/model`로 바꾼 직후에는 레일이 opus를 보여 주고 세션 정의는 fable로
남는 상태가 성립한다. 두 값이 어긋나 있다는 사실을 알리는 표시는 현재 없다.

### 1.5 정리

| 항목 | 내용 |
| --- | --- |
| 현상 | 데몬 재기동 이후 세션의 모델이 생성 시점 값으로 되돌아감 |
| 직접 원인 | 복원 실행의 명령줄에 생성 시점 값인 `--model=<alias>`가 부착됨 (`harness.py:844`) |
| 선행 원인 | `SessionDef.model`에 생성 이후 쓰기 경로가 없음 |
| 관측값이 어긋나는 이유 | UI의 모델 표시는 트랜스크립트 판독이고 세션 정의를 참조하지 않음 |
| 영향 | Fable 사용 한도에 걸린 세션이 재기동 후 작업을 진행하지 못함 |

## 2. 개선안 비교

### 2.1 방안 A: 관측된 모델을 세션 정의에 반영한다

트랜스크립트 판독에서 얻은 모델 식별자를 하네스의 별칭으로 되돌려
`sdef.model`에 기록하고 `sessions.json`에 지속시킨다. 복원은 갱신된 정의를
읽으므로 마지막으로 실제 사용된 모델로 올라온다.

이 저장소에는 같은 형태의 선례가 이미 있다. 대화 식별자는 세션이 실행된
뒤에 하네스가 정하는 값이고, 데몬은 그것을 관측해
`replace(session.sdef, conversation_id=...)`로 정의에 써 넣는다
(`manager.py:304`, `:455`, `:514`). 모델도 같은 성질의 값이다.

- 장점: 사용자가 별도로 조작할 필요가 없고, 세션 단위로 값이 유지된다. 레일
  표시와 세션 정의가 같은 값으로 수렴한다.
- 비용: 식별자에서 별칭으로 되돌리는 대응 관계를 선언해야 한다(3.1 참조).
- 한계: 판독이 아직 없는 세션(턴을 한 번도 돌지 않은 세션)은 생성 시점 값을
  유지한다. 이 경우는 원래 동작과 같으므로 회귀가 아니다.

### 2.2 방안 B: 복원 실행에서 `--model` 플래그를 생략한다

`harness.py:844`의 부착을 `restoring`이 참일 때 건너뛰면, Claude Code가
프로파일 설정 파일에 보존한 값으로 올라온다.

- 장점: 변경 지점이 한 곳이고 대응 관계 선언이 필요 없다.
- 문제: 1.3에서 확인한 대로 Claude Code의 보존 단위는 프로파일 하나다. 한
  프로파일을 여러 세션이 공유하는 구성에서는 모든 세션이 같은 값으로
  올라가며, 세션마다 다른 모델을 지정한 구성이 재기동에서 무너진다.
- 문제: 그 값이 어디서 왔는지 데몬이 알 수 없으므로, 세션 정의와 실제 실행이
  계속 어긋난 채 남는다. 1.4의 불일치가 해소되지 않는다.

### 2.3 방안 C: 모델을 바꾸는 명령과 API를 제공한다

`claunch sessions set-model <세션> <모델>`과 대응하는 API를 두어, 사용자가
명시적으로 세션 정의의 모델을 바꾸도록 한다. 세션 단위 설정을 바꾸는 선례는
`SessionManager.set_keep_alive`(`manager.py:1132`)에 있다.

- 장점: 동작이 명시적이고, 값의 출처가 사용자 조작 하나로 분명하다.
- 문제: Claude Code 안의 `/model`과 이중 경로가 된다. 사용자가 `/model`만
  쓰고 이 명령을 쓰지 않으면 현상이 그대로 재현된다.

### 2.4 권고

방안 A를 본체로 삼고 방안 C를 보조 수단으로 함께 둔다. 방안 B는 채택하지
않는다.

방안 A가 `/model`이라는 실제 사용 경로를 그대로 흡수하므로 사용자가 새로
기억할 조작이 없다. 방안 C는 턴을 아직 돌지 않아 판독이 없는 세션과, 다음
실행부터 다른 모델로 올리고 싶은 경우를 위해 필요하다. 두 방안은 같은 필드를
쓰므로 충돌하지 않는다.

## 3. 방안 A의 설계

### 3.1 모델 식별자와 별칭의 대응

하네스 레지스트리(`src/claude_launcher/harnesses.yaml`)에서 codex는
`model_aliases`로 별칭과 식별자의 대응을 이미 선언한다. claude 항목은
`models: [haiku, sonnet, opus, fable]`만 선언하고 대응 관계가 없다. 명령줄에
별칭을 그대로 넘기기 때문이다(`harness.py:845`).

역방향 대응을 세우기 위해 claude 항목에도 `model_aliases`를 선언한다. 다만
관측되는 식별자는 하나가 아니다. 조사에서 확인된 값은 다음과 같다.

```
claude-opus-5, claude-opus-4-7, claude-sonnet-5,
claude-fable-5, claude-fable-5-1, claude-haiku-4-5-20251001
```

한 별칭에 여러 식별자가 대응하므로 정확 일치만으로는 부족하다. 판정 규칙을
다음 순서로 둔다.

1. 레지스트리의 `model_aliases`를 뒤집은 표에서 식별자를 정확히 찾는다.
2. 찾지 못하면 하네스가 선언한 `models`의 각 별칭에 대해, 식별자가
   `<하네스 접두사>-<별칭>-` 또는 `<하네스 접두사>-<별칭>` 형태로 시작하는지
   본다. 접두사는 레지스트리에 `model_id_prefix`로 선언한다(claude는
   `claude`).
3. 둘 다 실패하면 판정하지 않는다. 판정하지 못한 식별자는 세션 정의를
   건드리지 않고 데몬 로그에 한 번 남긴다.

3번이 필요한 이유는, 판정하지 못한 값을 추측으로 메우면 사용자가 고르지 않은
모델로 세션이 올라갈 수 있기 때문이다. 판정 실패는 원래 동작(생성 시점 값
유지)으로 떨어지는 편이 안전하다.

### 3.2 반영 시점

`ctxsize.attach`는 API의 읽기 경로에서만 호출된다(`api.py:3578`의 레일 폴,
`:4361`의 상세 조회). 읽기 처리기에서 세션 정의를 쓰고 `sessions.json`을
저장하는 것은 조회 요청에 쓰기 부작용을 붙이는 형태이므로 채택하지 않는다.

대신 데몬의 기존 주기 작업과 같은 형태로 조정 작업 하나를 둔다. 각 주기마다
살아 있는 세션의 컨텍스트 판독을 읽고, 3.1의 규칙으로 별칭을 얻고, 그 값이
`sdef.model`과 다를 때만 `replace`로 갱신한 뒤 `persist()`를 한 번 호출한다.
값이 같으면 아무것도 쓰지 않으므로 평상시 비용은 판독 조회뿐이다.

갱신 시점의 판정에 쓰는 것은 가장 최근 판독 하나다. 그보다 앞선 판독은 이미
지나간 선택이므로 참조하지 않는다.

### 3.3 종료 직전의 반영

`SessionManager.persist`는 종료 절차에서 가장 먼저 실행된다(`manager.py:1494`
및 그 주석). 재기동 직전의 마지막 상태를 남기는 자리이므로, 주기 작업의
마지막 실행과 종료 사이에 일어난 모델 변경을 놓치지 않으려면 이 자리에서도
한 번 조정한다. 주기 작업과 같은 함수를 호출하면 되고, 별도의 규칙은 필요하지
않다.

### 3.4 값이 어긋나 있음을 드러내기

1.4의 불일치는 방안 A가 적용된 뒤에도 일시적으로 존재한다(`/model` 직후부터
다음 조정 주기까지). 이 구간은 짧고 스스로 해소되므로 별도 처리를 두지
않는다.

다만 3.1의 3번으로 판정에 실패한 경우는 스스로 해소되지 않는다. 이때는 세션
상세 조회 응답에 판정하지 못한 식별자를 실어, 사용자가 방안 C의 명령으로
직접 지정할 수 있게 한다.

### 3.5 변경 지점

| 파일 | 변경 내용 |
| --- | --- |
| `src/claude_launcher/harnesses.yaml` | claude 항목에 `model_aliases`와 `model_id_prefix` 선언 |
| `src/claude_launcher/daemon/harness.py` | 식별자에서 별칭을 얻는 함수 추가 (3.1의 세 단계) |
| `src/claude_launcher/daemon/manager.py` | 조정 함수 추가, `persist` 앞에서 한 번 호출 |
| 데몬 주기 작업 | 조정 함수를 주기적으로 호출 |
| `src/claude_launcher/daemon/api.py` | 판정 실패 식별자를 상세 조회 응답에 추가 |

방안 C의 변경 지점은 `manager.py`에 설정 함수 하나, `api.py`에 처리기 하나,
`cli_sessions.py`에 하위 명령 하나다. 설정 함수는 `harness.py:421-435`의 검증을
재사용해 하네스가 선언하지 않은 모델을 거부한다.

## 4. 검증 방법

단위 시험으로 세울 것:

1. 식별자에서 별칭을 얻는 함수가 3.1에서 열거한 여섯 개 식별자를 각각
   `opus`, `opus`, `sonnet`, `fable`, `fable`, `haiku`로 판정한다.
2. 같은 함수가 선언되지 않은 식별자에 대해 판정하지 않는다.
3. 조정 함수가 판독의 별칭과 `sdef.model`이 다를 때 정의를 갱신하고, 같을 때
   갱신하지 않는다.
4. 판정에 실패한 경우 정의가 그대로 유지된다.
5. 방안 C의 설정 함수가 하네스에 없는 모델을 거부한다.

실제 데몬에서 확인할 것(사용자가 재기동을 실행하는 자리다):

6. fable로 생성한 세션에서 `/model`로 opus를 고르고 한 턴을 돌린 뒤, 데몬을
   재기동하면 그 세션이 opus로 올라온다.

## 5. 미검증 항목

- Claude Code가 `/model`의 결과를 프로파일 `settings.json`의 `model` 키에
  기록한다는 점은, 해당 파일의 값이 `opus`이고 같은 프로파일의 트랜스크립트가
  `claude-opus-5`를 기록했다는 관측과 일치한다. 통제된 시험으로 기록 시점을
  직접 확인하지는 않았다.
- 명령줄의 `--model`이 `settings.json`의 `model`보다 우선한다는 점은 현상
  자체(재기동 후 fable로 올라옴)와 일치하지만, 두 값을 달리 놓은 통제된
  시험으로 확인하지는 않았다.
- 3.1에 열거한 식별자 목록은 조사 시점에 이 장비의 프로파일 하나에서 관측된
  값이다. 목록에 없는 식별자가 나타날 경우의 동작은 3.1의 3번이 다룬다.

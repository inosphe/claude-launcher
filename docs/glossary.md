# Workspace 용어집

대시보드의 **Glossary** (`#/glossary`)에서 workspace를 선택합니다.
용어·정의·별칭·출처를 직접 추가하고 기존 항목을 편집하거나 삭제할 수 있습니다.
별칭은 줄마다 하나씩 입력합니다. 제안 목록은 검토 대기·수락됨·거절됨으로
필터링할 수 있으며 수락과 거절 기록을 유지합니다.

## MCP 제안과 조회

`claunch mcp`에 세 도구를 추가했습니다. 기존 stdio 서버 프로세스는 다시
연결해야 새 도구 목록을 읽습니다. API와 페이지를 제공하는 데몬도 새 코드를
로드해야 합니다.

```json
glossary_suggest({
  "workspace": "claunch",
  "term": "기반 모델",
  "definition": "추가 학습을 시작할 때 사용하는 모델",
  "aliases": ["base model", "기반모델"],
  "source": "모델 비교 실험에서 사용한 정의"
})
glossary_search({"workspace": "claunch", "query": "base modle"})
glossary_resolve({"workspace": "claunch", "text": "[[term:기반 모델]]을 비교해주세요."})
```

`workspace` 생략 시 현재 세션의 등록된 작업 위치에서 workspace를 찾습니다.
관리되지 않는 MCP 프로세스는 현재 디렉터리를 사용합니다. 등록된 workspace가
없으면 오류를 반환합니다. 도구가 제출한 제안은 `pending` 상태이고 사용자가
웹에서 수락하면 용어로 등록됩니다. 거절된 제안은 이력에 남습니다.
이미 등록된 표준 용어와 충돌하는 제안을 수락하면 충돌을 표시하며 검토 대기
상태를 유지합니다. 기존 용어를 편집하거나 제안을 거절해 처리합니다.

## 짧은 용어의 검색

초기 검색 방식은 embedding 설정이 필요 없는 문자 기반 검색입니다.
NFKC·대소문자·공백·구두점 정규화, 표준 용어/별칭의 정확 일치, 부분 일치,
문자 유사도 순으로 정렬합니다. 한글 오타 비교에는 자모 분해를 사용합니다.
검색 결과는 매칭된 표기와 검색 방식, 유사도 점수를 보여줍니다.
점수는 확률로 해석하지 않습니다. 두 글자 이하의 질의에는 정확/부분 일치만
적용합니다. 뜻이 같은 다른 표기는 별칭으로 등록하면 검색에 포함됩니다.

이 방식의 의미 유사도 범위는 등록한 별칭에 의존합니다. embedding 도입 여부는
실제 용어와 질의의 정답 목록을 만든 후 문자 기반 검색 대비 후보 재현율,
상위 결과 정확도, 응답 시간으로 평가할 수 있습니다. 현재 구현에는 embedding
서비스나 RAG 인덱스 의존성을 추가하지 않았습니다.

## Quasi-quotation 적용 제안

[Racket의 quasiquote](https://docs.racket-lang.org/reference/quasiquote.html)는
인용한 구조의 일부를 `unquote`로 지정해 계산 결과를 넣는 방식을 제공합니다.
여기에는 **문장을 그대로 유지하고 명시한 용어 참조의 정의만 조회**하는 방식을
적용했습니다. 문장 전체의 의미를 자동 재해석하는 범위까지 확장하지 않습니다.

- `[[term:기반 모델]]`: 표준 용어나 별칭을 정규화하여 조회합니다.
- `[[term:#<id>]]`: 웹 카드와 검색 결과의 `reference`에 있는 안정적인 ID로 조회합니다.
- `\[[term:기반 모델]]`: 역슬래시가 바로 앞에 있으면 참조 조회를 생략합니다.

`glossary_resolve`는 원문 `text`와 위치(`start`/`end`, Python 문자열 인덱스),
`resolved`/`ambiguous`/`missing` 상태의 참조 목록을 반환합니다.
정확히 하나의 등록 용어를 찾으면 정의를 반환하고, 중의성이 있으면 전체 후보를
반환합니다. 오타 후보는 자동 확정하지 않습니다. 사용자가 후보의 ID를 선택한
뒤 다시 참조할 수 있습니다. 용어 이름을 편집해도 ID는 유지되고, 삭제한 ID는
`missing`이 됩니다. 일반 문장이나 정의 안의 참조는 재귀적으로 확장하지 않습니다.
정의는 데이터로 취급하며 코드나 명령으로 실행하지 않습니다.
웹 페이지의 **참조 확인**에서 이 결과를 미리 확인할 수 있습니다.
세션 입력창의 명시적 참조는 전송 직전에 해석하며, 원문 뒤에 선택한 정의의
JSON 스냅샷을 첨부합니다. 정의는 재귀적으로 확장하지 않습니다.

## 세션 입력창에서 사용하기

로컬 세션의 **type for this session** 입력창은 대상 세션의 작업 디렉터리에서
workspace를 결정합니다. 브라우저에서 마지막으로 열었던 용어집의 workspace와
독립적으로 결정하므로 다른 작업 위치의 정의가 섞이지 않습니다.

1. 일반 문장에 `자세히 설명해주세요`라고 입력합니다. 등록된 이름이나 별칭의
   표기가 감지되면 입력창 위에 `자세히 · 의미 2개` 같은 버튼이 나타납니다.
2. 버튼을 눌러 정의를 읽고 **이 의미로 바꾸기**를 선택합니다. 해당 위치만
   `[[term:#ID]]`로 바뀌고 전달할 정의가 입력창 위에 표시됩니다.
3. `[[term:자세히`를 직접 입력하거나 **용어집** 버튼을 눌러 검색할 수도 있습니다.
   이 검색은 별칭·부분 일치·문자 유사도를 사용합니다. 아래 화살표로 후보에
   포커스를 옮기고 Enter로 선택할 수 있습니다. Escape는 검색 영역을 닫습니다.
4. 전송 시 정의를 다시 조회합니다. ID가 삭제되었거나 이름에 여러 뜻이 있거나
   참조 표기가 미완성인 경우 초안을 유지하고 의미 선택을 요청합니다.
5. 해석이 완료되면 원문과 선택한 정의·출처·workspace를 한 메시지로 전달합니다.
   기존 입력 이력에도 실제 전달한 정의 스냅샷이 포함됩니다.

일반 문장의 감지는 등록된 이름/별칭의 표기를 대소문자 구분 없이 찾습니다.
영문 단어 내부의 부분 일치는 제외하고, 한글 조사·어미 앞의 용어는 감지합니다.
한 문장에서는 겹치지 않는 위치 최대 20개를 표시합니다. 정의 선택은 사용자가
수행하며 감지된 표현만으로 내용을 바꾸거나 추가 정의를 전송하지 않습니다.
여러 위치의 동일 표현은 각각 다른 의미를 선택할 수 있습니다.
자동 감지는 문자 그대로의 표기 기준이며, 오타 검색은 명시적 검색창에서 합니다.
한 번의 참조 해석은 원문 20,000자, 첨부 정의 JSON은 60,000자로 제한합니다.

### 하나의 표현에 여러 뜻 등록하기

각 의미에 별도 이름을 붙이고 같은 별칭을 등록합니다. 표준 이름은 workspace
안에서 정규화 기준으로 고유하며, 별칭은 여러 항목이 공유할 수 있습니다.

| 용어 이름 | 별칭 | 정의 |
|---|---|---|
| 자세히 · 구체적 설명 | 자세히 | 일의 목적과 동기, 실행 방법을 구체적으로 설명 |
| 자세히 · 추가 탐색 | 자세히 | 현재 모르는 일에 대해 브라우저 검색을 포함해 추가 탐색 |

`[[term:자세히]]`는 두 후보를 반환합니다. 선택한 ID를 사용하면 그 의미 하나가
전달됩니다. 위 표는 등록 예시이며 기본 데이터로 자동 추가하지 않습니다.

### 에이전트가 용어집을 인식하는 경로

기존 구현에서는 MCP의 도구 설명을 통해 기능을 알 수 있었고, 에이전트가
`glossary_search` 또는 `glossary_resolve`를 호출해야 정의를 읽을 수 있었습니다.
세션 시작 시 용어집 전체를 주입하거나 일반 메시지를 자동 해석하지 않았습니다.
도구 제공은 에이전트의 실제 호출을 보장하지 않습니다.

입력창 연동 이후에는 사용자가 선택한 정의가 메시지에 함께 전달되므로 해당
메시지를 해석할 때 에이전트의 선행 MCP 호출에 의존하지 않습니다. 전체 용어집을
매번 넣지 않고 참조한 항목만 첨부합니다. MCP는 별도의 검색·제안 경로로 유지됩니다.
이 입력 지원은 로컬 세션 입력창에 적용됩니다. 다른 머신의 shadow 입력창과
터미널에 직접 입력하는 키에는 적용되지 않습니다.

## 저장과 API

DB는 `<launcher home>/glossaries/<workspace 경로 SHA-256>.sqlite3`에 둡니다.
등록된 디렉터리가 저장 단위이므로 같은 workspace의 워크트리는 함께 사용하고,
workspace 이름 변경은 DB를 유지합니다. 디렉터리가 바뀌면 별도 DB를 사용합니다.
DB는 머신 로컬이며 설정 동기화나 git 커밋으로 복제하지 않습니다.
workspace 등록 해제와 용어 삭제는 각각 DB 파일과 제안 이력을 제거하지 않습니다.

API는 `?workspace=<이름>` 또는 `cwd`로 workspace를 지정합니다.
JSON 쓰기 요청에서는 같은 값을 본문에 넣을 수도 있습니다.

| 동작 | 경로 |
|---|---|
| 검색/목록 | `GET /api/glossary?q=...&limit=100` |
| 추가 | `POST /api/glossary` |
| 편집/삭제 | `PUT` / `DELETE /api/glossary/<id>` |
| 제안 등록/목록 | `POST` / `GET /api/glossary/suggestions` |
| 검토 | `POST /api/glossary/suggestions/<id>/review`, `decision: accept/reject` |
| 세션 입력 검색 | `GET /api/sessions/<name>/glossary?q=...` |
| 세션 입력 분석/전송 준비 | `POST /api/sessions/<name>/glossary`, `text`, `action: analyze/compose` |
| 명시적 참조 | `POST /api/glossary/resolve`, `text` |

검색은 요청당 최대 100개를 반환합니다. 정의는 최대 10,000자, 용어/별칭은
각각 최대 200자, 별칭은 최대 50개입니다. 동일한 대기 제안의 재전송은 중복
등록하지 않습니다. 제안의 중복 검사와 등록, 수락은 각각 SQLite 쓰기
트랜잭션으로 처리하여 동시 요청에서도 동일한 대기 제안과 수락된 용어가
하나씩 생성되도록 합니다.

# cflow2 저장 내구성과 손상 복구

## 저장 구조

`<cwd>/.cflow2/runs/<scope>/checkpoint.sqlite3`가 생성된 런에서는 이 파일이
상태·워크플로 정의·이벤트·영수증의 정본이다. `state.json`, `chart.json`,
`journal.jsonl`, `receipts/`는 사람이 확인할 수 있는 사본이다. 사본을 직접
수정해도 실행 상태는 변경되지 않는다.

상태 변경과 그 변경의 이벤트는 SQLite 트랜잭션 하나에서 확정한다. 설정은
rollback journal(`DELETE`), `synchronous=EXTRA`, `fullfsync=ON`이다. DB 커밋
이후 JSON 사본을 갱신한다. JSON 저장 실패는 로그로 보고하고, 이미 확정한
작업의 성공 여부를 바꾸지 않는다. 상태·정의·이벤트·영수증에 SHA-256을 함께
저장하여 조회 및 복구 시 내용의 무결성을 검사한다.

프로세스가 트랜잭션 도중 종료되면 SQLite가 이전 확정 상태로 rollback한다.
커밋 직후 JSON 저장 전에 종료되면 새 상태와 이벤트를 DB에서 읽는다.
JSON이 NUL로 바뀌거나 없어져도 정상 DB가 있으면 실행 상태를 읽을 수 있다.
DB 자체가 손상된 경우에는 JSON 사본으로 자동 전환하지 않는다.

이 보장은 운영체제와 저장장치가 동기화 요청을 이행한다는 조건을 전제로 한다.
디스크 고장, 파일 전체 삭제, 저장장치의 잘못된 flush 응답은 별도 백업이
필요하다. 프로세스 강제 종료 테스트는 실제 전원 차단 검증을 대체하지 않는다.
SQLite의 동기화 보장은 [공식 PRAGMA 문서](https://www.sqlite.org/pragma.html#pragma_synchronous),
하드웨어·운영체제 가정은 [Atomic Commit 문서](https://www.sqlite.org/atomiccommit.html)에 따른다.

외부 명령, 메시지 전송, Git 작업은 이 DB 트랜잭션에 포함되지 않는다. 외부
작업 완료 직후 기록 전에 중단된 경우에는 실제 결과를 확인해야 한다. 저장
내구성만으로 외부 작업의 exactly-once 실행을 보장하지 않는다.

## 기존 런 전환

정상 JSON만 있는 기존 런은 다음 저장 시 정의, 상태, 저널, 영수증을 검증하여
DB를 만든다. 이전 저널의 잘못된 줄을 무시하면서 전환하지 않는다. 이미 손상된
런은 전환을 거절한다.

전환 후 구버전 코드가 같은 런을 쓰면 JSON과 DB가 달라질 수 있다. 배포 시
데몬과 해당 런의 MCP 서버를 모두 새 버전으로 맞춘 뒤 쓰기를 재개해야 한다.
에이전트가 공유 데몬을 직접 재기동하지 않는다. `archive`는 DB 및 복구 증거를
함께 보존한다.

## 점검 및 복구

런이 있는 디렉터리에서 실행한다. 아래 `<scope>`는 대상 세션 이름이다.

```text
claunch cflow2 recover --scope <scope>
```

이 명령은 워크플로를 진행시키지 않는다. SQLite 무결성, 각 내용의 해시,
런의 scope 및 정의 일치를 검사하고 `run`, `revision`, `updated`, `active`,
`differences`를 출력한다. SQLite 자체의 미완료 트랜잭션 rollback은 조회 시에도
발생할 수 있다. `differences`는 DB와 다른 JSON/영수증 사본의 목록이다.

복원하려면 **에이전트 세션 밖의 사용자 터미널**에서 방금 확인한 리비전을 지정한다.

```text
claunch cflow2 recover --scope <scope> --apply --revision <revision>
```

적용 시 다음 처리를 한다.

1. 런 잠금을 획득하고 리비전을 다시 검사한다. 달라졌으면 적용하지 않는다.
2. 기존 사본과 검증한 체크포인트 내용을 `recovery/<고유 id>/`에 보존한다.
3. `storage_recovered` 이벤트와 `storage-recovery` 보류를 확정한다.
4. 상태·정의·저널·영수증 사본을 DB의 확정 내용으로 다시 쓴다.

복구 과정에서 워크플로 명령을 재실행하지 않는다. 복원 후 외부 명령의 결과,
보드, 커밋, 위임 작업을 확인한 뒤 사용자 터미널에서 보류를 해제한다.

```text
claunch cflow2 resume --scope <scope> storage-recovery
```

복구 도중 다시 중단되어도 DB에 기록된 보류는 유지된다. `recover`를 다시
조회하고 새 리비전으로 적용할 수 있다. 이미 실행 중인 외부 프로세스를 이
명령이 중단시키지는 않으므로, 복구 적용 전에 대상 런의 작업을 정리한다.

## 복구 자료가 없는 경우

`no durable checkpoint`는 새 저장 구조가 적용되기 전의 런이라는 뜻이다.
특히 `state.json` 전체가 NUL인 기존 s995 런은 새 코드를 설치하는 것만으로
복구되지 않는다. 저널에는 상태 전체가 기록되어 있지 않아 정확한 상태를
재구축할 수 없다.

이 경우 런 디렉터리를 별도 위치에 보존하고, 정상 시점의 전체 백업이 있으면
그 백업의 런 신원과 외부 작업 결과를 확인한다. 정상 백업도 없으면 남은
정의·저널·보드 기록으로 완료된 작업을 정리한 후 새 런을 시작한다. 손상된
상태 파일을 빈 객체로 대체하거나 이벤트만 추정 재생하지 않는다.

DB 자체가 손상된 경우에도 원본을 보존하고 정상 백업을 확인한다. 실행 중인
DB의 파일 하나를 단순 복사하는 방식은 일관된 백업을 보장하지 않는다.
백업에는 SQLite Backup API를 사용하거나 해당 런의 모든 writer를 정지한
상태에서 런 디렉터리 전체를 보존한다. hot journal(`checkpoint.sqlite3-journal`)이
있으면 함께 보존한다. 이 복구 명령은 손상된 DB의 페이지를 추정 복원하지 않는다.

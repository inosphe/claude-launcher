# 테스트 찌꺼기 색인과 삭제 계획

이 문서는 `CLAUNCH_TEST_DIR` 격리(커밋 `1e6f8c11`, `cdf8658b` — claunch-pyv3d,
2026-10-21)가 들어오기 전에 테스트가 남긴 산출물을 색인하고, 그것을 어떤 순서로
지울지 정한다. **이 문서는 계획이다. 실제 삭제와 권한 변경은 사용자가 한다.**

색인은 `tools/test_debris_index.py`가 만든다. 이 문서의 수치는 그 도구를
2026-10-22 17:2x KST에 돌린 결과이고, 기계는 계속 테스트를 돌리므로 값은 분
단위로 움직인다. 다시 재려면 같은 명령을 다시 돌린다.

```
uv run --no-sync python tools/test_debris_index.py            # 색인 + 배치
uv run --no-sync python tools/test_debris_index.py --measure  # 파일 수·바이트까지
uv run --no-sync python tools/test_debris_index.py --json     # 기계가 읽는 형태
```

## 왜 이 색인이 필요한가

2026-10-22, `/`의 inode 67,108,864개 중 여유가 8만여 개(100%)로 떨어졌고
바이트는 506 GB가 남아 있었다. 데몬의 sqlite 쓰기가 `OSError: [Errno 28]`로
실패해 thread API가 500을 냈고(claunch-zbu54), 같은 시간대 스윕 job이
error 3,318건으로 실패했다(claunch-slia4.1).

테스트 산출물은 한 루트 아래에 모인다 — `pytest_basetemp.root()`, POSIX에서
`<런처 홈>/basetemp`. 세션이 끝나면 exit reaper가 그 세션 몫을 지우지만 세 가지
형태가 남는다:

1. **고아(orphan)** — 레지스트리에 없는 세션 이름의 디렉터리. 어떤 세션의 exit도
   이 이름과 매치되지 않으므로 reaper가 영원히 집지 않는다.
2. **0200 디렉터리** — 목록 조회 권한이 없어 reaper가 `locked`로 기록만 하고
   남긴다. 2026-10-22 현재 `basetemp-history.jsonl` 10,033행 중 9,135행이
   `locked`다(claunch-zbu54). 커밋 `f79542a3`이 회수 경로를 고쳤지만, 이미
   남은 49개는 그대로다.
3. **held 세션의 트리** — 지우면 안 되는 것이 맞다. 다만 세션이 held인 채로
   오래 남으면 inode 예산을 계속 차지한다.

## 소유 판정

소유를 정하는 네 가지를 전부 `daemon.basetemp_reaper`에서 가져온다: 이름 규칙
(`owner`), 레지스트리 디렉터리 집합(`registry_dirs`, 기준은 `paths.base_home()`),
레코드 읽기(`registry` — `sessions.db`, 없으면 레거시 `sessions.json`), 그리고
live 판정(`live_name` — running 또는 held). 이 도구는 그 넷을 다시 구현하지
않으므로 두 곳이 같은 디렉터리의 주인을 다르게 볼 수는 없다. 어긋남이 생긴다면
그것은 그 모듈 자체가 바뀐 것이다.

중요한 방향은 하나다 — 살아 있는 세션의 트리가 `ended`로 읽히면 아무도 다시
보지 않는 삭제 배치에 들어간다. 리뷰에서 잡힌 두 경우가 정확히 그 자리였다:
`sessions.json`만 남은 인스턴스와 `CLAUNCH_INSTANCE_BASE`가 설정된 경우.
둘 다 테스트로 고정했다.

reaper의 이름 규칙에 걸리지 않는데 **이름이 살아 있는 세션으로 시작하는** 항목은
네 번째 판정 `ambiguous`로 보낸다(`s29d`, `s29om` — 2026-10-22 배치 A에서
손으로 보류한 5개, 510 inode. 그 중 `s29w2`는 #387이 reaper의 이름 규칙에
`<세션>w<숫자>`를 넣은 뒤 `live`다). 어떤 삭제 배치에도 들어가지 않는다. 이 가드는
orphan에만 적용한다: 배치 B 후보는 정의상 live 세션이 소유한 트리이므로 같은
규칙을 대면 428/428이 제외되어 B가 0건이 된다.

| 이름 모양 | 만든 곳 |
| --- | --- |
| `<세션>c<MMDDHHMMSS>` | `tools/changed_tests.py` (실행마다 하나) |
| `<세션>w`, `<세션>w<숫자>` | `tools/sweep.py` (뒤의 것은 고정 이름을 못 쓴 뒤의 세대) |
| `<세션>-<임의>` | 세션이 손으로 지정한 basetemp |
| `<세션>` | `$CLAUNCH_TEST_DIR`, 세션의 일반 테스트 디렉터리 |

이름은 중첩되므로(`s29`는 `s29w2`의 접두사다) **가장 긴 일치**가 주인이다.
`held_at`이 있는 세션은 프로그램이 끝났어도 세션이 살아 있는 것이므로 `live`로
읽는다 — resumable이기 때문이다.

## 삭제 계획

### 배치 A — 지금 지울 수 있는 것 (약 402,122 inode)

순서가 있다. 앞 단계가 뒤 단계의 전제다.

1. **repair 49개** — `chmod -R u+rwX`로 탐색 비트를 되살린다. 이 단계 없이는
   어떤 도구도 그 디렉터리를 지우지 못한다(`rmdir`도 `Directory not empty`로
   실패한다). 되살린 뒤 그 49개를 지운다.
   repair는 **삭제 후보만** 받는다: 상태를 읽기 여부보다 먼저 보므로 `live`와
   `ambiguous`는 0200이어도 여기 들어오지 않는다. 순서를 뒤집으면 가드가 한
   줄 뒤에서 무너진다(0200인 live 트리가 "chmod 후 삭제" 목록에 실린다 —
   리뷰에서 잡혔다).
2. **orphan 23개** — 주인이 없으므로 기다릴 이유가 없다.
3. **stale 5개** — 종료된 s201의 것이고 하루가 넘었다. reaper가 집었어야 할
   몫이다.

측정된 회수량은 402,122 inode다. 0200 49개의 실제 크기는 chmod 뒤에 다시 재야
한다.

### 배치 B — held 세션의 오래된 트리 (정책 결정 필요)

live 781개 중 하루가 넘은 것은 528개다. 이들을 지우면 held 세션이 resume될 때
그 basetemp를 잃는다 — 대부분 다시 만들어지지만, 실패를 되짚던 세션에게는
증거가 사라지는 일이다.

`tools/changed_tests.py`의 `prune_basetemps`는 이미 실행 중인 세션에 대해
**최신 8개만 남기고** 지운다. 같은 규칙을 held 세션에 적용하는 것이 자연스러운
후보다: 세션마다 최신 8개를 남기고 그보다 오래된 `<세션>c*`만 지운다.
`s29`가 348개, `s90`이 49개를 들고 있어 이 배치가 가장 큰 회수량을 낸다.

이 배치는 사용자의 승인이 필요하다. 이번 회차는 수치만 낸다.

### 배치 C — basetemp 밖

`/tmp`에 `claunch-vscode-1000-*` 빈 디렉터리 1,340개가 있다(각 1 inode).
`/tmp`는 머신 전역이므로 다른 세션의 것이 섞여 있다. 회수량이 작고 판정 비용이
크므로 마지막 순서다.

### 배치 D — 세션 scratch 아래 linked worktree

`$CLAUNCH_SCRATCH`가 런처 홈 안에 있어서, 거기 만든 linked worktree는 세션의
저장소에 등록된 채로 세션보다 오래 산다. 2026-10-22 측정: `git worktree list`
**443줄**, 그중 런처 홈 아래가 **308개**, 판정상 제거 가능이 **172개**.

```
uv run --no-sync python tools/test_debris_index.py --worktrees [--repo <저장소>]
```

판정은 넷이고, 하나라도 걸리면 남긴다.

| 판정 | 조건 |
| --- | --- |
| 보호 | 그 경로의 세션이 live(held 포함) |
| 보호 | 그 세션을 어떤 레지스트리에서도 찾을 수 없다(`unknown`) — basetemp의 orphan과 달리 워크트리는 exit 훅이 다시 보지 않으므로 "주인 없음"은 "종료됨"과 같은 증거가 아니다 |
| 보호 | 커밋을 가리키는 ref가 하나도 없다 — 지우면 그 커밋은 복구되지 않는다 |
| 보호 | `git status --porcelain`이 비어 있지 않다(미커밋 변경) |
| 제거 가능 | 종료된 세션 · 깨끗함 · 커밋이 어떤 ref에서든 도달 가능 |

삭제는 `git worktree remove <path>` 뒤 `git worktree prune`이다. `rm -rf`는
등록을 남겨 다음 사람이 그 경로를 다시 찾지 못하게 한다.

## 이 색인이 세우지 못한 것

- **basetemp가 전체 inode의 몇 %인지.** 측정된 348개에서 6.3M inode를 확인했고
  `df -i`의 사용량은 67.0M이므로, basetemp 밖에 더 큰 소비처가 있다. 이번
  측정은 그것을 가리지 않는다. 원인 미상.
- **0200 49개의 실제 크기.** 권한이 돌아오기 전에는 셀 수 없다.
- **509개 디렉터리의 정확한 inode 수.** 측정은 전체 순회라 느리고, 이 머신에서는
  다른 세션의 테스트와 I/O를 나눠 쓴다. 배치 A의 후보 77개는 전부 쟀다.

## 승인 경계

이 회차가 한 일은 색인과 계획까지다. `chmod`, `rm`, `rmdir`은 실행하지 않았다 —
실제 홈의 산출물 삭제는 사용자 승인이 필요한 일이다(`.claunch/prompts/test-isolation.md`
규칙 6, claunch-gziru.1 선례). 데몬 재기동·정지도 하지 않았다(AGENTS.md).
